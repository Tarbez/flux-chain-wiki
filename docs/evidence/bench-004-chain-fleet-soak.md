# BENCH-004 · Six-node chain-fleet soak

Measured 2026-10-08 from an Apple arm64 client against the six public
`chain-server` endpoints. This is accepted-finality throughput over the raw TCP
wire path, not a durable-finality or cumulative-ledger measurement.

## Method

For five minutes, one `fleet-many` process per node repeatedly submitted 32
holder chains × 500 entries. The six processes ran concurrently from the same
client and therefore shared its CPU and network origin. Each node returned one
`K` acceptance per entry. The run continued through in-flight batches and ended
after 303.152 seconds.

| Node | Batches | Accepted | Failures |
| --- | ---: | ---: | ---: |
| bk2 | 37 | 592,000 | 0 |
| mk2 | 36 | 576,000 | 0 |
| bk1 | 37 | 592,000 | 0 |
| mist1 | 33 | 528,000 | 0 |
| eug-2c | 45 | 720,000 | 0 |
| eul-4c | 47 | 752,000 | 0 |
| **Fleet** | **235** | **3,760,000** | **0** |

The measured fleet average was **12,403 accepted ops/s**. Each operation in
this benchmark is one admitted signed `LEDGERENTRY`. Multiplying the
earlier 1.52 million single-node result by six would predict about 9.12 million,
but that is not what simultaneous load produced. Shared client CPU, one network
origin, node latency, and server contention are part of this result and must not
be factored away.

The hourly `/api/fleet-pulse` value is a separate short capacity sample. Its
`total_entries` field is the 4,800 synthetic entries generated by that pulse,
not the number stored by the fleet. The server does not yet publish a cumulative
cumulative operation counter.
