# The world as its own grammar

> Moved 2026-10-29: `MESH.md`, the mesh library and the editor docs now live in the `fxn-3d` repo (`flux/fxn-3d/docs/design/world-grammar/MESH.md` and `flux/fxn-3d/docs/design/editor/`). This site imports the engine through `scripts/lib/fxn-3d.mjs`.

For the owner and the engineer who will build the next 3D world of defxn.com. Measured 2026-10-29, WebKit 26 (Playwright 1.56) at 1440x900, the local server on port 3438 with no compression, on an 8 GB Mac. The site code is at commit e3a92bb; nothing here changes it yet.

The world is built the LLM way: a 724 KB library builds a scene graph of objects at start, every page's stage is loaded and compiled whether the camera goes there or not, and the scene's facts travel as JavaScript objects (JSON in a different costume: `js/content/network-data.js`, `records-sample.js`, the `-data.js` files). The frame cost is then paid on the CPU each frame by walking that graph.

## The rethink

The world becomes a resolver of its own, with its own grammar. The atlas rule applies (`flux/flux-grammar-atlas`, "Two kinds of grammar"): a resolver built off the chain defines its own grammar and nothing is reserved there. So the labels below mean what this file says, in this resolver only. The network registry is not touched.

Three parts:

1. **Records.** Every fact of the world is one record: a ring, a cube, a callout, a knob, a view's camera, a page's exit. The encoder derives them from the owner's data; nobody types them.
2. **Frames.** The settled picture of each view is compiled once, at build time, into one content-addressed blob of instance matrices and colours. A record names the blob and its parts. The browser decodes a frame straight into GPU buffers. A flight is the camera moving plus the vertex shader blending two frames by one number. No scene graph exists in the browser.
3. **The wire.** One text, `world.flx`, holds every record for every view. Blobs are fetched by content id with an immutable cache. Boot is two requests plus the blobs of the first view.

### The laws of this grammar

- A record is a row of boxes split on `-`. `-` is the only delimiter and never appears in a value.
- Each box belongs to the longest label it starts with. Labels are single uppercase letters, so no label can capture another. The atlas's collision audit was run over all 25 labels: zero findings that need a person.
- The value is checked against the label's payload rule. The reader is generated by the atlas (`world-reader.mjs` here), never hand-written.
- A record that the reader refuses is never written. The encoder reads every record back through the reader before it writes the file. This caught two bad records on the first run: a parent of `-1` (the minus sign is a dash) and a callout kind outside the chain kinds.
- Numbers are text, not floats on the wire: `m` is minus, `p` is the point. `m30p5` is -30.5. Decoding is deterministic text to number; no float formatting is ever trusted.
- Free text enters as hex of UTF-8. This grammar has no free text yet; names are lowercase alphanumeric from a derived set.
- Large bytes are never inlined. A frame's matrices and the mark image travel as content-addressed blobs named by a `C` box (the dense-encoding rule for long content).
- Closed sets are derived from the data where the data defines them (callout kinds come from `LABELS`), and are written by hand only where the set is the design's own (record kinds, knob groups, mesh parts).

The input shape the atlas designer takes is `world-grammar.labels.json`, so the grammar can be opened there, checked again and exported as a node grammar without re-describing it.

### The records, from today's data

`world/world.flx` is the real scene, derived by `scripts/world-encode.mjs` from `network-data.js` and `world-data.js`: 123 records, 4,178 bytes, of which 40 are the frame and part records of the four slice-1 views and 12 are the chains inside networks (their picture spots projected back through the design camera). The same facts take about 18,000 bytes today across three files.

```
WRING-I0-Khub-X300-Y185-D200-Q16-SH
WRING-I1-Kidentity-X57-Y100-D88-Q12-SL
WCUBE-X205-Y15-SL
WLABEL-Fidentity-X57-Y44
WKNOB-Glook-Nkeystrength-V2p3
WKNOB-Glook-Nkeyx-Vm30
WEXIT-Rhome-Eup
```

A frame and its parts, the two record kinds the encoder adds at build time:

```
WFRAME-Rintro-C<64 hex>-A<bytes>
WPART-Rintro-Mtile-O0-A1248
WPART-Rintro-Mlink-O79872-A620
```

One `WPART` is one draw call: the part's instances start at byte `O` of the frame's blob and there are `A` of them.

## Encoder and decoder

**Encoder** (`scripts/world-encode.mjs`, build side, Node): reads the owner's picture data and the knob file once, runs the stage placement maths of `js/world/*` once per view to get each instance's settled matrix and colour, writes the blobs by content id, derives the records, reads every record back through the generated reader, and writes `world.flx`. Nothing is hand-authored. A change to the picture or a knob is a rerun, and a new frame blob gets a new content id, so caches never go stale.

**Decoder** (browser): the generated reader, a decode of records into typed state, and a small WebGL2 renderer with one program per family of parts plus the post passes: eight programs (lit, dots, flat, the key light's depth pass for the parts and one for a mounted mesh, bright, blur, comp), not 66. It uploads a frame's blob as instance buffers and draws one call per `WPART`. A flight binds the old and the new frame and blends them in the vertex shader by one uniform; the camera moves on the CPU as now. Hover lift, the build-up on first visit and the beam's glow stay as time functions in the shaders. The world still draws on demand and settles (the site's animation law).

No Three.js, no scene graph, no `renderer.compile` of hidden stages, no stage files loaded for pages the camera never visits.

## Migration

Future law: the old data files are read once by the encoder and never rewritten. The current world stays live until the owner confirms the new one on screen. Slice 1 was confirmed on screen 2026-10-29. `tests/world-grammar.cjs` locks it. Every record reads through the generated reader. The encoder is idempotent (two runs into temp dirs, byte-identical to each other and to `world/`). Every frame's byte count is its parts' instances x 64 with every part inside its blob. The atlas audit over the labels has zero findings. After the confirmation the floor and the halo came in as seven more parts (`grid`, `orbit`, `pool`, `mark`, `catch`, `halo`, `port`), one record (`WLOGO`), two tones (`--primary`, `--primary-300`) and the shadow map. CONTRACT.md has each one's unit shape and placement.

## What is not decided

- Whether the glow pass stays at all, or returns only on screens above 3.2 million pixels.
- Whether the first-visit build-up stays a shader time function or becomes two frames (empty, built) blended like a flight.
- The `CUBES` and `LABELS` of the picture are still picture coordinates (601x436). The encoder should project them into world units once, so the browser never knows the picture existed.
